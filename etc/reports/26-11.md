## Watching repositories and linked worktrees

This month's headline feature clearly must be native filesystem monitoring support coming in via `gix-notify`. It provides 4 backends, kqueue and fsevents for macOS, inotify on Linux, and however Windows calls theirs (it's longest name of them all). And everywhere else, the `notify` crate is used to bring validated support for FreeBSD for instance.

With the primitives in `gix-notify`, the equally new `gix-fsmonitor` crate provides a client for the fsmonitor server for its IPC protocol, and the server implementation itself, and also a daemon implementation for good measure. With it it's easy to implement your own daemon, or embedded fsmonitor compatible servers. The latter will be very useful for `starship`, which very soon can daemonize itself to provide fsmonitor services to… itself and Git, far faster prompts in huge repositories, even if these aren't officially configured for it. This has the potential to greatly speed up Windows as well and I am looking forward to trying it there. That of course would be unfeasible if you'd end up with 10 `starship` daemons hanging around forever, so they will shutdown automatically after a given idletime, a feature that the Git fsdaemon doesn't seem to have.

And finally, based on `gix-notify`, there now is `Repository::monitor()`, which allows to watch all files relevant to a repository. It can be used, for instance, to auto-reload configuration when it changes, or to watch files change in the main and linked worktree, with built-in gitignore support so one won't get overwhelmed with massive amounts of changes in fully ignored directories.

And what's best is that based on this, *incremental git status* is coming, to give long-running applications the benefits of the git fsmonitor, more efficiently and without actually needing it.

## `gix-merge`, finally with Git index compatibility.

There were a couple of PRs with fixes to `gix-merge` by people who encountered issues and diversion from Git. While that was to be expected, once these start to trickle in, they usually won't stop until one does something drastic, like… changing the last portions of code that affected `gix-merge` and led to differences with Git:

- Previously, `gix-merge` for trees would do two tree diffs, and then try to reconcile the change from each pair of trees while rebuilding the destination tree. This had many problems, and would probably never lead to equivalency. So it was rewritten to do its own Git tree-walk across all three trees at the same time, collecting all needed data while at it.
- The `gix-diff` generic rename tracker now tracks only file renames, without gather additional data for directory renames which probably never really worked all that well. Thus, `gix-merge` extracts its own directory rename information which is needed as it has more information.
- The algorithm for integrating tree changes changed completely to be similar to what Git does. While a bit slower despite many optimisation rounds, it's now arriving at the same result in all the tested cases.
- The merge index creation was completely overhauled to produce the same conflicting entries, but also invalidate the TREE and UNTR extensions after copying them from a reference index. This is critical to keep `git status` fast after such a merge completed.

Oh, and submodule merges are now supported as well, so it really does seem like this could be the definitive version of `gix-merge` (maybe with a future bugfix here and there).

## Preparations for a stable `gix` release

Here it comes: I am pushing for incremental stability now. The general plan is to leave most, but not all, plumbing crates in major-zero land, but elevate *parts* of foundational plumbing crates into stability.

This works with `gix-macros` ability to selectively remove annotated functions, methods, and types that are marked `#[unstable(since = "YY-MM-DD")]`. This way, only the needed portion of a crate will be exposed.
While this works doesn't work for plumbing crates if they expose types with unstable fields or methods, but it will work with care.

The plan is to use `unstable` to gate most of the `gix` API alongside stabilizing portions of a few foundational crates. With the first `gix` 1.0 release, it will support stable usage of exactly one downstream consumer (the one which uses the smallest API surface). Then each month, a new downstream consumer should follow.

The minor release of `gix` 1.X means "0 or more new features" for those who don't set the "unstable" feature for `gix`, and "possibly breaking changes" for consumers who do. This also means that `gix = "~1.0" allows to update only patches, which is needed for those who use "unstable", but don't want to be broken outside of their control.

Alongside this machinery, I have improved `cargo smart-release` to be able to perform actual API compatibility checks with `cargo semver`, so version bumps don't have to be conservative anymore. Instead, they can be done when needed, without letting accidental breakage slide.

This is the best I could come up with, and think it will work, feedback is welcome.

Realistically, the first stable release will happen in March next year though as I expect most consumers to require `gix-ref`, and that will see a lot of changes for when reftable support lands.

## Trust-improvements

The notion of `Trust` is special in Gitoxide as it allows to open any repository even without its mention in `safe.directory`. On the flip-side, this also means that this better be implemented correctly so untrusted configuration and data can't sneak through.

Trust is based on ownership, so non-owned repositories aren't trusted as long as one of the important directories, common-dir, git-dir or the worktree dir aren't owned by the current user.

However, these checks also take time, so if performance matters to this point, it's now possible to open with `gix::open::Options::default().with_enforced_trust(Trust::Full)`, and no check will be performed.

The same is true when reducing trust, of course.

Lastly, there now is a way to register a callback to configure which options sub-repositories like linked worktrees, or submodules, are opened with, returning full control to the user.

## Community

### Sirocco now writes, too

In October, [Sam Reis](https://github.com/srijs) provided us with much faster decompression using `Sirocco`, and now he [did it again](https://github.com/GitoxideLabs/gitoxide/pull/3127) by optimizing write compression to be up to 40% faster!

In an [experiment](https://github.com/ivankovic/omnidiff/pull/66), `Omnidiff` and its single-threaded census got sped up 3.1x by using Gitoxide.

### Faster `packed-refs` rewrites

[Yilin Chen](https://github.com/FYWinds) added an optimisation that avoids an unnecessary revalidation when deleting from a `packed-refs` buffer. They [showed](https://github.com/GitoxideLabs/gitoxide/pull/3193) how the deletion of a single ref in a one-million-refs file took 13.57 seconds, and then went down to 141 milliseconds. [#3193]()

### Fast object database lookups

[Mark Blum](MarkBlum-Shopify) improved tree-diff lookups in repositories with many packs by keeping recently used indexes [near the front](https://github.com/GitoxideLabs/gitoxide/pull/3186). 
This is similar to an optimisation that Git received. This will benefit each thread that accesses the object database individually.
