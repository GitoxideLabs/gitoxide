## Git notes!

I was probably already a 10-year Git user when I finally discovered Git notes, and I found them incredibly intruiging. How cool is it to attach arbitrary metadata to any Git object? Imagine the cool things one could build with that - review, issue tracking, metadata in general!

And another couple of years later, it's safe to say that none of this materialised, and that it's more of a niche feature.

But `tix` motivated me to make good use of it, so here we are with `gix::Repository::notes()` for query and edit. `tix` uses it for per-worktree metadata like a todo-tag, notes, but also a 'qa-pass' marker for trees, which naturally goes away if the tree changes again, indicating QA would have to be redone.

All in all, super-useful for building custom tools to support *your* workflow, and I certainly have all reasons to use them more in future.

## Signing of commits and tags, and verification

My work on `tix` motivated me to finally tackle signature verification and signing itself, and OpenPGP, X.509, and SSH are all supported and tested. In that process, `gix-testtools` also got a bunch of signing-related primitives to facilitate this kind of testing everywhere.

## TIX!

The `tix` CLI has been making great strides, and it already is my daily driver. It now supports edits with automatic rebasing, a new way to handle conflicts, and even sports a special "review" tool which I use for reviewing all contributions.

That review tool also just automates a previously cumbersome process:

- create a new commit at the base of what's to be reviewed
- checkout the worktree at the top-most commit to review (so one can review multiple commits at once)
- re-add each hunk to the index, and make changes at will during refactoring
- once the worktree is clean, and the commit contains all changes + refactorings, put this review commit on the top-most commit of the stack under review.

The last step, which finishes the review, is notably not a cherry-pick, as this would conflict. Instead it just adopts the exact tree from the commit, which naturally exposes my refactors.

Despite the usual hassle of fully generated tooling, like degeneration and old issues popping up again, the overall trajectory is towards "it's getting better". It's also a delight to see that it's possible to create such tooling at all.

In any case, `tix` already is an incredible help to learn which concepts work, and which don't, so `gg` can start with the right ideas and concepts from the get-go.

## A fully-functional `fetch` implementation!

For the longest of times, the delta-resolution algorithm has two major problems, from deal-breaker to problematic:

1. thin-packs with in-back objects couldn't be handled
2. parallelism didn't work well for imbalanced delta-trees, and it consumed too much memory.

Problem 1 meant that fetches didn't work for Azure DevOps hosted repositories at all, and some GitHub repos had the same problem. It was a bit of a hit and miss and a complete dealbreak. Now it's able to schedule deltas for resolution once it has seen their bases, and the rest is just business as usual.

Problem 2 could mean that the repositories like phpstan would take multiple times longer than Git *and* use a lot of memory. `crossbeam-deque` is the key to workstealing, solving the performance problem, and a better way of handling buffers (and their lifetime) leads to optimal performance in both speed and memory consumption.

All in all just a couple of hundred lines of code, and a mild refactor on top made everything so much cleaner. Admittedly, this wouldn't have happened without an agent, and I definitely learned some new tricks in the lengthy refackiew process.

## Greater Robustness

Both fuzzers and LLMs keep probing the codebase and they keep finding issues, which are typically fixed the same day.

One I want to highlight particularly as there was a fix to what feels like a day-one bug that would cause an infinite loop when a lock was held that triggered a specific error, and trying to collect error information then caused an endless loop ([#2921](https://github.com/GitoxideLabs/gitoxide/pull/2921) prevents infinite lock-error parent traversal). The fix was trivial: actually update the cursor while walking a chain (`while let Some(cursor) {... cursor is never updated here ...}` was the problem).

## Greater conformity tree-merging with merge-ORT

Clearly another great use of LLM: Increasing code coverage, writing baseline and cartesian tests, along with fuzz tests, to trigger many more issues in the current code, and then fix it.
Benchmarks are easy to generate as well, and the primary usecase is to protect performance across changes.

This is what happened to `gix-merge` which now is much more conformant to merge-ORT than ever before, and remembering how time-consuming this work was when I did it back in the day, LLMs truly are a god-sent.
